- `sbx create/run -t IMAGE` runs a sandbox from any container image, and `sbx template load` imports an image from a tar file. There is no `sbx build`.
- **No Docker on the host.** sbx sandboxes have their own Docker engine (verified: `docker build` and `docker save` work inside one). Build flow:
  1. Create a builder sandbox **with no workspace**: `sbx create --name paddock-build-N shell`, then copy the build context in: `sbx cp FOLDER paddock-build-N:/tmp/ctx` (Paddock copies a filtered copy of the context, see Build context). (Verified: sbx refuses a read-only primary workspace, `primary workspace must be read/write`. Copying in is stricter anyway, because the builder cannot write to the project.)
  2. In it: `cd /tmp/ctx && docker build -t paddock/N:HASH -f DOCKERFILE .` then `docker save -o /tmp/image.tar paddock/N:HASH`.
  3. `sbx cp paddock-build-N:/tmp/image.tar <host temp>`, then `sbx template load <tar>`, then `sbx rm --force paddock-build-N`.
  4. `sbx create -t paddock/N:HASH --pull never ... AGENT FOLDER`.
- The Dockerfile is agent-editable (so untrusted), and its `RUN` steps execute inside the builder microVM, never on the host. The builder gets the same network policy as the project, plus the registries the base image needs.
- **Implemented (`ImageBuild`, `ImageBuilder`), fixture-tested, first real build on the Mac is PAD-2:** create builds the image when `.paddock.toml` has an `[image]`. The builder `paddock-build-<project>` gets the project's network plan (global rules, its confirmed hosts, llmman denied, no gateway); the context goes to `/tmp/paddock/ctx` and the Dockerfile to `/tmp/paddock/dockerfile/` (`sbx cp`, after `mkdir -p`); `docker build --progress=plain` gets the tag, the Dockerfile, and `--build-arg K=V` as arguments of a fixed script, never as script text; build argument names must be letters, digits, and `_`. The builder is removed afterwards, also on failure, and a failed build shows docker's last 30 lines. The sandbox is created with `--template paddock/<project>:<hash> --pull never` (without `--pull never` sbx would pull it from Docker Hub). The project's other `paddock/<project>` images are removed after a create.
- **Build context:** before a build, Paddock copies the context into a private folder outside the project (0700, removed afterwards, also on failure), keeping only what the ignore file lets through, and the build reads that copy, never the project folder. The ignore file is `[image] dockerignore` when set, else `<Dockerfile>.dockerignore` next to the Dockerfile, else the context's `.dockerignore`; none means everything. Rules are docker's (moby patternmatcher: `*` and `?` within a segment, `**` across segments, `[...]`, `\` escapes, a leading `/` is the root, `!` exceptions, the last match wins, a folder's match covers what is inside it; an excluded folder is walked only when an exception starts with its path), except that regex characters such as `+` or `(` are literal. The ignore file must be a plain file, not a link. Links in the context are copied as links only when they stay inside it (as written and as resolved; a dangling one only without `..`); others, and sockets, pipes, and devices, are skipped and named in the Log. Files are cloned (APFS) where possible. The Log shows the copy as files, bytes, and how many entries the ignore file left out. The copy's Dockerfile folder holds the Dockerfile and the deciding ignore file as `<Dockerfile>.dockerignore`, so docker, which finds that name first, applies the same rules again; in the builder sandbox both go to `/tmp/paddock/dockerfile/`, and with `[images] builder = "docker"` the Mac's `docker build` gets the staged Dockerfile and context too, so both builders see the same files. (`BuildContext`, `DockerIgnore`, PAD-69.)
- **Tag:** `paddock/<project>:<12 hex>`, a hash of the Dockerfile, its build arguments, the Dockerfile and context paths, the `dockerignore` path when set, and the agent section; not the approval digest, so changing only hosts or ports in `.paddock.toml` does not rebuild. An image sbx already lists is not built again. Files the Dockerfile `COPY`s from the context are not in the hash, so changing one alone does not rebuild (PAD-70). A sandbox name that is not a valid image name (uppercase, `.`, a trailing `-`) gets a short hash of itself in the repository, so two projects never share one.
- **Drift:** sbx does not report a sandbox's image, so the project file records the tag it was created from (`imageTag`). When the approved Dockerfile asks for another tag (or `.paddock.toml` no longer names one), Sync lists "recreate" for it (confirmed first, like any recreate).
- The image must stay compatible with the agent, so a project Dockerfile should start `FROM` the agent's base image: `docker.io/docker/sandbox-templates:<flavor>`, e.g. `claude-code-docker` or `shell-docker` (the `-docker` flavors include a Docker engine). `sbx template ls --json` returns `[{id, repository, tag, flavor, created_at, size}]`; the operator's own Claude templates show `flavor: "claude-code"`, but images loaded with `sbx template load` may have no `flavor`, so Paddock records which agent each built image is for.
- The builder sandbox uses the `shell` agent (`shell-docker` image).
- sbx commands that ask for confirmation refuse to run without a terminal (`sbx template rm` says `pass --force`), so Paddock always passes `--force` after its own confirmation in the UI and never leaves an sbx prompt waiting.

- **Folder check (FolderPolicy):** reject a project folder that is `$HOME` or `/`, contains `$HOME`, or that is, is inside, contains, or has a direct child linking to (compared case-insensitively, links followed) one of the home folder's `FolderPolicy.sensitiveEntries`: `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/Library`, `~/.kube`, `~/.docker`, `~/.azure`, `~/.config/gh`, `~/.config/gcloud` (PAD-83). The same names elsewhere are the project's own and are not refused: when a new project's folder has one as a direct child, the New Project sheet names them and the operator confirms before it is created (`FolderPolicy.sensitiveNames`, PAD-137). The same check guards every extra folder, with one exception (PAD-125): an extra folder the operator adds in Paddock (Info or New Project, `ExtraFolders.check`) may be inside `~/Library/Logs` (not `~/Library/Logs` itself; links followed first, so a link out of it is judged by where it points), so Paddock's logs and hang captures can be shared with an agent. Such a folder is always mounted read-only (`ExtraFolders.readOnly`, at add and at every create, whatever the project file says; its Read-only box cannot be cleared), and the field warns that it may hold other apps' logs. A project folder and a project's `sbxenv.yaml` workspaces never get the exception (`FolderPolicy.check` without `allowingLogs`).
- **Claude sessions folder (PAD-127):** when the operator chose it for a Claude Code project (New Project or Info), Paddock mounts `${XDG_DATA_HOME:-~/.local/share}/paddock/sessions/<project>/claude` at `~/.claude/projects` through its own mixin kit's `host-mount@1`, bound with `sbx create --mount`, or for a project with an `sbxenv.yaml` with a top-level `mounts:` entry in Paddock's own overlay (PAD-130; `mise run capture:cli sessions-env`). sbx would take `mounts:` from a project's file too: Paddock refuses that key there (`ProjectEnvironment`), so only Paddock binds a host folder. It is in Paddock's data folder, never its config folder. At every create Paddock makes it if missing (owner only), refuses it when any part from Paddock's data folder down is a link or not a folder, and checks it with `FolderPolicy` (so it may not overlap the config folder). The kit never goes without `--mount` (sbx would mount a folder of its own that every sandbox with the kit shares), and the create reads the mount back from `sbx ls --json` (the CLI; the socket does not list a kit's host mounts) and removes a sandbox that mounted anything else. The agent writes the folder, links included, which show as links on the Mac (`mise run capture:cli sessions-hostmount`): Paddock never follows anything in it; Clear Sessions removes links as links. sbx 0.51.0 keeps no kit `volume@1` across a recreate (PAD-127), so a folder on the Mac is the way.
- **Paddock config dir:** reject a project folder that is, contains, or is inside `~/.config/paddock` (or its XDG override). The app config and project list live there, so an agent must never see or edit them.
- **Mounts:** the chosen folder, and the extra folders the operator added in Paddock (PAD-73.5), are the only things ever mounted. sbx itself allows any path (`filesystem:* **`), so these checks are the only guard. An extra folder is added only in Paddock's interface (the Info tab or the New Project sheet), never from a file in the project, and is kept in Paddock's project file. It passes `FolderPolicy` like a project folder, links followed, when added and again at every create (`ExtraFolders.checkAll`; a folder that fails stops the create). It may not be, hold, or sit inside the project folder or another extra folder, nor have a colon in its path (sbx reads `PATH:ro`). It is read-only unless the operator switches it, and one that is another project's folder is marked. Tests: `ExtraFoldersTests`.
- **Network:** a sandbox gets sbx's global rules plus its kits' hosts, the project's `sbxenv.yaml` kits only once the operator confirmed that exact version (fingerprint), less the hosts they declined (sandbox denies); Paddock denies only what protects its own services: llmman's port always, other projects' gateway ports when an allow reaches them (see Network policy).
- **Models:** agents reach models only through the ModelGateway (route allowlist, one port per project, model pinning, loopback only, plus the sbx HTTP rule as a second layer). Paddock never passes `--model`. Local models and the embedded llmman UI are disabled while any llmman hardening check is red.
- **Kits:** Paddock's kits come only from `paddock.yaml`, and a local one there may not be inside a project folder. A project's `sbxenv.yaml` may name only sbx's catalog kits and its own local kits inside its folder (v3 mixins, no links, only the capabilities Paddock accepts: no credentials, SSH agent, or host mounts), confirmed with the file.
- **Project file:** `sbxenv.yaml` is untrusted. Paddock refuses one that runs commands on the Mac (`lifecycle`), sets secrets, bindings, registries, mounts, MCP servers, or Paddock's own environment, or publishes ports on Paddock's services or the Docker API; and it creates with `--skip-host-commands`. Paddock's own part goes in an overlay in its config dir, never in the project folder. Tests: `ProjectEnvironmentTests`, `EnvironmentReviewTests`, `ProjectRunnerTests`.
- **Browser:** the browser an agent drives runs only inside its sandbox. The browser tab's web view keeps no data and reaches only the dashboard's loopback origin. A native show tab's Markdown is rendered by Paddock (`MarkdownPage`): every piece of text escaped, raw HTML shown as text, a CSP with no scripts and images only from `paddock-file:` or `data:image/`, links only relative, http(s) or mailto (and the navigation policy still refuses all but the tab's own files), and the web view runs no JavaScript (tests: `MarkdownPageTests`).
- **Voice:** audio never enters a sandbox: the Mac transcribes (SpeechAnalyzer, on-device) and speaks (AVSpeechSynthesizer), and only text crosses. The agent cannot open the microphone; `paddock-voice ask` only shows a banner. What the voice kit sends is checked (`VoiceMessage`: fixed kinds, length, choice and word limits) and cleaned before it is shown or spoken (`SpokenText`: no control, bidi, or zero-width characters, no markdown, plain text, never SSML), and every utterance starts with the project name, so an agent cannot sound like Paddock. Dictation is pasted as a bracketed paste without control characters, not submitted unless the operator turned that on. Answers and dictation records go into the sandbox on standard input, never in argv (backlog doc Voice).
- **Gateway callers:** a request whose `Host` is not loopback, `localhost` or `host.docker.internal`, or that carries an `Origin`, gets 403 before routing, so a web page in the operator's browser (or a DNS-rebinding page) cannot use the model (PAD-82). The gateway also bounds open connections (`maxConnections`) and logs its 429s (PAD-88).
- **Approval to use:** after `sbx env create` the files are read again; a different fingerprint than the confirmed one removes the new sandbox and fails the create (PAD-84). Catalog kits are not pinned by digest yet (PAD-85).
- **Host processes:** `FoundationProcessRunner` ends a command that prints more than 64 MB per stream or runs longer than 15 minutes (`ProcessLimitError`; PAD-87). The environment is still inherited (open point in PAD-87).
- **Config folder:** `~/.config/paddock` and what is in it are owner-only (0700 and 0600), repaired at every load (`PaddockPaths.secure`; PAD-94). Approvals are not signed: a process running as the operator can still change them.
- **Secrets:** Paddock stores none and manages no agent logins or API keys; those are sbx's (`sbx secret set`, which the operator runs). Gateway sandboxes use the dummy key `paddock`.
- **App settings:** App Sandbox off (Paddock runs `sbx` and reads `~/.config`), Hardened Runtime on with one entitlement, `com.apple.security.device.audio-input` (push-to-talk), ATS `NSAllowsLocalNetworking` so the web views can load localhost.

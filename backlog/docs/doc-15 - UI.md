- **Title:** a breadcrumb path in the detail's title bar (`Breadcrumb`, such as Projects > app); the plain title is hidden. Earlier steps are links, gray like the rest of the path and darker under the pointer, which turns into a hand; the last step is the page itself.
- **Project view:** one tab bar, or two side by side: the standard split view (`HSplitView`, a divider to drag). A tab's context menu moves it to the other half ("Move to Right Half", "Move to Left Half"), and so does dragging it onto the other half's tab bar; its session keeps running. The right half appears when a tab moves there and goes when it is empty; it has no Info and its "+" opens sessions there. **Info** is the left half's first tab, an icon only (see Project Info), orange when something waits for the operator (a pending port request, files to approve, or differences). Then one tab per session: agent sessions (`sbx run --name N`, "agent", "agent 2") shells (`sbx exec -it N bash`, "shell", "shell 2"), and shells on this Mac ("mac", "mac 2", a laptop icon): the operator's login shell (`$SHELL -l`, zsh when unset) in the project folder, not in the sandbox. **+** is the one place new tabs open, in two sections: Sandbox (New Agent Session, New Shell; these create the project's sandbox first when it has none) and This Mac (New Shell on This Mac, which needs no sandbox). The toolbar's Shells menu opens things outside Paddock: Sandbox Shell in Terminal, Shell on This Mac in Terminal (the operator's terminal app, through a `.command` file), and Show in Finder. While no agent session is open, a dimmed, dashed "agent" tab sits after the others; clicking it starts one the same way. A session that ended offers Run Again. **Terminal themes:** each project may pick the colors of its terminals in Info's Terminal row (Default, or one of `TerminalTheme.all`: Solarized Dark, Dracula, Nord, Gruvbox Dark, One Dark, Tokyo Night, Monokai, Solarized Light, GitHub Light, each with its own background), so its sessions look unlike other projects'; it is kept in the project file (`terminalTheme`), applies to all its terminal tabs at once, and changes them live. Selecting a project (in the sidebar) puts the keyboard in the terminal of its selected tab: the left half's, else the right half's (`ProjectTerminals.focusSelectedTerminal`, through `SandboxTerminalView`'s `focus` request, taken once the view is in its window). So does selecting a session tab in either half's bar (a click, on the shown tab too) and opening a new one (`ProjectTerminals.setTabs`). Sessions keep running while another project is shown and end with the app. Each session's terminal view lives as long as its tab (`TerminalViewCache`): showing the tab again (from Info, another tab, another project, or the other half) puts the same view back, live and unchanged, instead of building a new one that replays the scrollback; a replay of a full-screen program's trimmed output came out blank and held up the main thread. A session's process starts once its terminal view is laid out, so a full-screen program (OpenCode, for example) gets its startup queries (size, capabilities) answered live, at the real size; sizes under 40x10 (a view still being laid out) are never sent; the size is sent again (with a `SIGWINCH`) 1 s, 3 s, and 8 s after a sandbox session's first output, the last time one row shorter and then at the size, since sbx can miss the start size or a resize while it starts and the program then draws for another size until the operator resizes the window (PAD-57; a shell on this Mac has no sbx in between and gets none), and a view that replays the scrollback answers the queries in it only if no view was live when they came. A tab shows the title its program sets (OSC 0/2, for example Claude Code's "✳ Claude Code" or its spinner while it works), with a leading symbol as the tab's icon; the title is untrusted sandbox output, so control, bidi, and zero-width characters are dropped and it is cut to 60 characters.
- **Status marks (PAD-33, PAD-63):** each project shows one mark, the same in its sidebar row, its card, its toolbar, and the Status row of Info (`ProjectBadge`, drawn by `ProjectBadgeView`): its sandbox's own state, nothing about its agents. In order: **needs you** (orange `exclamationmark.circle.fill`: an approval request waits for the operator), **running** (small green dot), **changing** (grey half dot: a state sbx reports that is neither running nor stopped, in sbx's words), **problem** (red triangle: such a state with error, fail, dead, unhealthy, or crash in it; sbx named none in the captures), **stopped** (grey ring), and nothing without a sandbox. Each differs by shape, so color only adds to it, and nothing pulses: the operator never has to watch a mark to read it. Entering "needs you" bounces the symbol once. The tooltip (and VoiceOver) says it in words, for example "running, 2 approval requests waiting for you"; Info's Status row shows those words. **Agents** have marks of their own (`AgentTabMarks`, `AgentMarkView`): **waits** for the operator (orange exclamation), **working** (green ellipsis), **finished** while not looked at (accent checkmark, until the operator opens the tab), idle (a faint ring). An agent tab carries its mark after its name, and so does a shell tab an agent runs in; host tabs (the Playwright tab) carry theirs on their icon's corner. A tab counts as looked at only while its project is shown and Paddock is the active app, so an agent that finishes while the operator is on another project or in another app gets its finished mark.
- **Agents in the sidebar (PAD-63, PAD-64):** under each running project, one row per agent, always listed (no collapsing, so a waiting agent is never hidden) and in a stable order (`SidebarAgents.rows`): its agent tabs and the shell tabs an agent reports from, in tab-bar order (left half first), then the agents started outside Paddock, by session. A row shows the agent's mark, what its tab shows (the title the program set, such as Claude Code's task summary, without its leading symbol; else the tab's name, "agent 2" or "claude in shell"; wrapping to at most three lines, cut at the end, with the mark and the time on its first line and the tab's name in the tooltip), and how long it has been in its state ("waits 3m", "working 40s", "done 12m", "idle"; updated every 15 s); its tooltip says it in words. Clicking a row shows the project with that tab selected and its terminal focused, which clears its finished mark, and the row stays selected. The sidebar follows the tab bar: selecting a tab that has a row (in either half; the last one selected counts) selects that row, any other tab (Info, a shell without an agent, a browser tab) the project's row. An agent started outside Paddock (its session names no tab) is a dimmed row with nothing to open (not selectable), shown only when the kit recorded its process, so the status kit's watcher ends it once the agent is gone (backlog doc Kits, Agent status), and not shown once idle for over an hour. A session that names a tab Paddock no longer has (closed, or from an earlier launch) gets no row, and neither does a session from a kit before PAD-64, which records no process and so would stay for a day after its agent died. Idle rows are dimmed too. A stopped sandbox lists no agents.
- **Resources (PAD-32):** sbx has no stats API (its own dashboard runs a short /proc script in each sandbox through its exec endpoint), so Paddock runs `SandboxTop`'s scripts through `sbx exec N sh -c ...`. They need only sh, cat, tr, head, df, sleep (and getconf for the page size, else 4096), so no image needs ps, and every line carries a tag so a missing tool drops only its own line. Nothing polls in the background: **Info, Resources** (under the status) shows CPU, memory, and disk as bars (green, orange from 75%, red from 90%) and the load average, read every 5 s only while Info is shown (CPU from the difference to the previous reading, so it appears with the second). Its **Processes** button opens the **Processes tab** (a host tab like the Playwright tab: closable, movable to the other half, kept while the sandbox stops): a table of every process by app (an app is a program, or for an interpreter like node or python the script it runs, so Chromium's dozen processes are one row that opens into them), with PID, CPU in Activity Monitor's terms (100% is one CPU, over one second from two `/proc/<pid>/stat` snapshots), resident memory, and command, sortable by each, read every 5 s only while the tab is shown. One `sbx exec` costs about 0.25 s and 0.12 s of the Mac's CPU; the process script about 30 to 80 ms of CPU in the sandbox. **Never starts a sandbox:** `sbx exec` starts a stopped one, so both read only while the sandbox runs and no action of Paddock's is under way (`SandboxTop.mayPoll`). A stop from outside Paddock in the moment a script starts could still be undone by it; the event stream ends reading once it reports the stop.
- **Processes (PAD-31, PAD-58):** a page in the sidebar's System section (System > Processes selects it; there is no window of its own and the status popover has no button for it) is a table of the current user's sbx-related processes on the Mac from `ps` (`HostProcesses`, `SbxProcesses.classify`): kind, process, PID, CPU (ps's average), memory, how long it runs, command, sortable by each. Kinds, in this order: **no terminal** (an sbx command whose parent is gone: a forgotten dashboard keeps reading every sandbox), **left by Paddock** (watchers; Paddock stops these itself at launch, backlog doc Kits, Watchers), **in a terminal**, **Paddock** (its watchers), **sandbox machine** (one `containerd-shim-nerdbox-v1` per running sandbox, shown by its container ID; which sandbox it belongs to is not in sbx's output yet), and **sbx** (the daemon, llmman, Sbx.app's helpers). "Stop Them..." and the rows' context menu stop only processes without a terminal or left by Paddock, after a confirmation that lists them, with SIGTERM to processes still the same (the list is read again, so a reused pid is left alone); nothing outside sbx and Paddock is listed (Activity Monitor's job). The list is read every 30 s and when the window opens, and the status button gets a small orange mark while sbx commands without a terminal exist.
- **Templates (PAD-72):** a page in the sidebar's System section (`TemplatesView`): every image `sbx template ls --json` lists, in a table (kind, image, agent flavor, size, created, used by) with the count and total size above it, grouped by what each is, from its name (`TemplateUsage`): old project images (`paddock/...`, from Paddock's image builds before PAD-73.4; nothing uses them), other images, kit builds (`sbx-kit-src:...`, a local kit sbx built at a create; built again at the next create that names it), and agent templates (`docker/sandbox-templates:`, `sbx/`, `docker/sbx-kit-`; downloaded again for new sandboxes of that agent). sbx does not report which image a sandbox runs, and the page says so. **Remove...** (a button and the right-click menu, for one or several) asks first, naming each image (at most 8; any more are counted with their size in one line, so the dialog fits the screen, PAD-80), its size, and what removing it means, then runs `sbx template rm --force` for each; `ProjectRunner.removeTemplates` checks against a fresh `sbx template ls` first, so one gone meanwhile is reported, not removed. Removals go to the Log; a failure shows in the status button. **Not yet checked on the Mac (PAD-72):** that sbx downloads a removed agent template again by itself, and what a stopped sandbox does when its image is gone.
- **Network, Filesystem** (sidebar, System): Paddock's own versions of sbx's dashboard panels, read with `--json` (no TUI). **Network** is the rules and the network log as one table (columns: decision, sandbox or "all", target, kind, source, seen, connections, rule, actions): every network and HTTP rule from `sbx policy ls --json`, one row per host (a rule naming 40 hosts is 40 rows, each showing its rule; removing a rule says how many hosts go with it), in scope order (all sandboxes first, then each sandbox; the chosen sandbox first when filtered), with a Sandbox column and the log merged in (`RulesTable.merging`): each row shows when the hosts it covers were last seen and how many connections it let through or blocked, and every host a sandbox reached (or tried) that no rule names is a row of its own ("no rule"), with Allow and Deny. **Paddock's suggested denies** are rows too, one per sandbox that can reach them and does not deny them yet, from a short list: the Docker API (2375 and 2376, under both loopback names) and cloud metadata (`169.254.169.254`). Paddock does not apply them on its own; Deny does. Suggestions show disabled (greyed) until they are applied. Filters: the sandbox (all, or one: then only its section, on top, and the rules for every sandbox below it show, with its own activity; a project's shortcut opens the page on it), a search, the decision (all, allowed, denied, suggested), and activity (any, seen, blocked). Each row shows its source (sbx default, kit (the agent's, the project's, or Paddock's), added, approval, organization, Paddock, suggested by Paddock, no rule) and its actions wherever sbx allows one: allow, deny, or remove a sandbox's own rules; apply Paddock's suggestions; answer approval requests; **Deny for SANDBOX** on any allow from an sbx default, an agent kit, the organization, or a global rule (a sandbox deny beats it; the rule stays for the others), for a kit's own sandbox or the sandbox the page is filtered to; host services for this Mac's ports (allow, remove, deny for one sandbox); remove a global rule (confirmed first). **+** in the Network page's title bar blocks a host for every sandbox (a global sbx deny, confirmed first, as it changes every sandbox) or for one (a sandbox deny, a host rule; preset to the sandbox the page is filtered to). No actions on Paddock's own service denies, the gateway's HTTP rules, global denies (no sandbox allow beats a deny), or filesystem rows (sbx offers no command for them that is captured). The activity comes from `sbx policy log --json` (`SbxPolicyLog`: `{"allowed": [...], "blocked": [...]}`, each entry the sandbox's name as `sandbox_id`, `host:port`, proxy type, the matching rule or why none did, the reason when blocked, a count, and first and last seen; a host can have several entries, one per HTTP request the proxy judged on its own, which add up), read with the sandboxes' rules and ports. **Filesystem** lists sbx's filesystem rules and every sandbox's mounts, with the same sandbox filter. CPU and memory, which sbx's dashboard shows, are not in any JSON captured so far (PAD-19). The rules table's columns sort by a click on their header, again to reverse; until then rows keep their scope order (PAD-123). The sidebar's Network item counts the denies Paddock suggests (none when zero; from the rules alone, in a label of its own so network activity does not redraw the window), and so does the Suggested filter (PAD-123).
- **Live activity** (from the events, over the socket or the CLI alike): the `policy.network` replay is the whole network log and each live event replaces or adds one entry (`SbxPolicyLog.apply`; one entry per sandbox, host, decision, proxy type, and rule; verified against `sbx policy log` on 0.49.2), so the Network page updates as connections happen ("just now" in the Seen column) and `sbx policy log` is read only while the events are down. Network events re-read a sandbox's rules at most every 30 s. A project's Info has **Recent Activity** (`ActivityTimeline`, memory only, 50 per sandbox; each entry also goes to the Log as Sandbox activity, and so to its file): lifecycle, published ports, and each host reached or blocked for the first time, from the live events only (the replay is state, not news). **Approval requests** come from `approvalUpdates()`: sandboxd's `/user-prompts` stream (any line after the replay reads the list again; also every 15 s) or, through the CLI, `sbx policy approval ls` every 10 s. They show as a count in the sidebar, as a banner under the project's terminal (a row of its own under the terminal, in the left half when both halves show one; Allow, Dismiss; no keyboard shortcut, Return belongs to the terminal), and, while Paddock is in the background, as a macOS notification for requests that arrived since launch (Allow needs an unlocked Mac; clicking opens the project; answered requests are taken back). The status checks say where reads come from (socket, CLI and why, or a newer sbx API with the capture command), and a tortoise beside the status button marks CLI reads.
- **Notices:** every notice on the Info tab (warnings, an `sbxenv.yaml` to confirm, differences with Apply or Recreate, suggestions, approval requests) is one `NoticeRow`: an icon for its kind, the text, its buttons on the right, on a tinted background (orange for warnings and changes, yellow for suggestions and requests).
- **Project Info:** two columns (stacked in a narrow window). Left: the project's details as a label/value list (status, agent, provider, folder, extra folders (each with Read-only, Show in Finder, and Remove, a mark when it is another project's folder, and Add Folder; a change shows as a recreate item, since sbx mounts folders only at create, PAD-73.5), gateway and clone mode when they apply, published ports, created, last used), Needs attention when something does, and two shortcuts with counts (rules, blocked, suggestions; mounts and filesystem rules) that open the Network and Filesystem pages on this sandbox. Right: the ports. Hosts are allowed and denied on the Network page. The project's actions are in the title bar, aligned right: its state (a dot and its name, or the name of the action running, such as "Starting the sandbox"; no spinner), Create (no sandbox) or Start (stopped), then one **stop and remove** button: a click takes the mildest step the project can take now (Stop when running, else Remove Sandbox, else Remove Project), and its arrow or a right click offers every step it can take (Stop, Remove Sandbox, Remove Project), each doing the ones before it first (`AppModel.tearDown`: Remove Project on a running project stops it, removes the sandbox, then deletes the project file, each step after the last one succeeded). Stop runs at once; a remove step asks first, saying what it will do. Last, the **shells menu** (a terminal icon): Sandbox Shell in Terminal (the sandbox's shell, `sbx exec -it N bash` as in the shell tab, in the operator's own terminal app; disabled while the project has no sandbox); then Shell on This Mac in Terminal (the operator's login shell on the Mac, `$SHELL -l`, started in the project folder; not the sandbox) and Show in Finder. The terminal-app items go through a `.command` file Paddock writes to its folder in the user's temporary folder and opens (`ExternalShell`; no Automation access needed; values single-quoted; the script removes itself when it runs). Config (edit `sbxenv.yaml`, written first with a kit when there is none; backlog doc Project config file) is an icon next to Show in Finder in the folder row. With an `sbxenv.yaml`, Kits shows as two rows: Project kits (the file's) and Paddock kits (the choice from paddock.yaml, Edit Kits). Refresh is in the title bar of the other pages.
- **Voice (backlog doc Voice):** one popup at the bottom right of the terminal. In an agent tab whose project has the voice kit, a microphone (right-click for Voice reply and Hands-free); clicking it, or Option-Space, opens the panel above it, which stays open: what is heard (clicking into the text pauses to edit it), one row of pills and buttons: Listen (red while on), Voice reply (the agent ends with a spoken summary or asks out loud; off, it replies in the terminal as usual), and Hands-free (sends on its own 4 s after you stop talking, the pill showing "Sending in N s" meanwhile; turning it on turns on Voice reply; "stop" said on its own holds it, "send" sends at once; and listens for the answer to a question), Send (pastes it into the agent's prompt and presses Return; while an agent is read aloud it is Cancel, which stops the speech), and a close button: the panel stays open after Send or an answer until it is closed there. The panel starts with the conversation: what the agent said and asked (left; questions purple) and what the operator sent (right), newest at the bottom. Anything the agent says (`paddock-voice say`) or asks (`paddock-voice ask`) opens the panel by itself; a question adds its choices as buttons, a field to type, and Dismiss. Voice reply decides only whether it is also read aloud. No keyboard shortcuts in it: Return belongs to the terminal.
- **Models pane:** llmman's own web UI in a WKWebView, loaded only when all hardening checks are green.
- **Tooltips** show after 0.2 s (`NSInitialToolTipDelay`). The rules tables' actions are icons on a grid of three left-aligned slots (allow-type, deny-type, remove), each kind always in its own slot, with short tooltips (such as "Deny for claude-plane"). The row under the pointer is slightly highlighted.
- **Version (PAD-104):** the running build's version, `yymmdd.N`, sits next to the status button (`VersionLabel`, `AppVersion`): the day of the commit the build is from (the Mac's time zone) and how many earlier commits on the first-parent line that day (0 for the first), so 261106.2 is the third commit of 6 November 2026. `tools/tasks/version.sh` (`mise run version`) computes it from git; `mise run build` and `mise run install` set it as `CFBundleShortVersionString`, the commit count as `CFBundleVersion`, and the short hash as `PaddockCommit` (with `-dirty` for uncommitted changes), so About Paddock shows it too. Nothing is bumped by hand. Its tooltip names the commit and says when the build had uncommitted changes; the text is selectable. A build from Xcode alone keeps project.yml's placeholders and shows "unversioned".
- **System menu** (PAD-119): a top-level menu for Paddock itself, like the sidebar's System section: Log (Shift-Cmd-L) and Processes select their pages; Verbose Log; Log Files shows this session's log file in Finder; Crash Reports (as in the status popover); Capture Diagnostics (below); Edit Paddock's Config.
- **Hang capture** (PAD-121): a watchdog thread (`HangWatchdog`, no Swift tasks) asks the main thread every 2 s; when it has not answered for 6 s it captures Paddock once (`HangCapture`: sample 5 s, footprint, vmmap summary, heap, open files, the system log of the last 10 minutes, and Paddock's log file) into `~/Library/Logs/Paddock/hangs/<time>/` with a `summary.txt`, at most once per hang and every 10 minutes (`HangWatchdogClock`; a watchdog that was itself held up, as when the Mac slept, starts over). The log file says so at once; when the main thread answers again the Log says how long it was stuck and where the capture is. System > Capture Diagnostics captures the same on demand and shows the folder in Finder. spindump needs sudo and stays in `mise run hang`. Whether `sample` reads a Release build (Hardened Runtime) is not yet verified (PAD-121).
- **Status button:** in the sidebar's title bar next to New Project (there is no status bar). One dot, green when sbx runs, nothing is missing, and every llmman hardening check is green, yellow otherwise; its tooltip counts what needs attention. It flashes red when an error arrives. Clicking it opens the last error, every check (dependencies, sbx, llmman's hardening checks and loaded models, the gateway) with their fix actions (copy the install command, Clear prompt history), Crash Reports (macOS's `~/Library/Logs/DiagnosticReports` in Finder, Paddock's newest `.ips` selected), and Refresh. Refresh is always available: it finds the tools again, starts a new check that takes over from one that is stuck, and reads sbx's sandboxes, ports, and rules again; a check that takes over 30 seconds is given up with a message. **Log** (PAD-59) is a page in the sidebar's System section (System > Log and Shift-Cmd-L select it; the status popover has no button for it): this session's lines (or an earlier session's, see below), oldest first, at most 5000, as one read-only text in columns: time, category (`LogCategory`), source, message. An error line that arrives while it is not shown puts a red dot on its sidebar item until it is shown (PAD-122). System > Verbose Log (the `verboseLog` default, off at first; PAD-119) adds lines marked `[verbose]` that say why things happen, so far what became of each voice message. Categories: Paddock (errors the status popover showed, the app's own messages), Setup (what a create did, step by step), Sandbox activity (each project's Recent Activity, with why a host was blocked), Voice, and Processes. Source is what a line came from when it is one thing: the project's sandbox, and for voice the agent tab (`app · agent 2`); an error that names a project has that project. A selection spans any number of lines and Cmd-C copies it; a long message wraps under its column as the page resizes, and the text follows new lines while scrolled to the bottom. A toggle per category chooses what shows: none chosen shows every category, each one chosen adds to the choice (remembered across launches); All/Errors shows only errors, and a field filters by message or source (`LogFilter`). Copy All copies the lines shown in full, Clear clears the session's lines. Every line also goes to a file of the session's own in `~/Library/Logs/Paddock`, one per launch, named by when the app started and its process id (`paddock-2026-10-30_08-25-50-4711.log`, `LogFiles`; Paddock and Paddock Dev never share one, and `mise run hang` takes the stuck app's), as `time [ERROR] [category] source: message`, or `-` in place of `source:` when there is none, so a line reads back unambiguously (`LogEntry(fileLine:)`). A source never holds ": ". Lines from background work (a create's steps) are written to the file at once, from the thread that reports them, and reach the page when the main actor gets to them, so the file keeps them even while the UI is stuck (PAD-78). **Earlier sessions:** a picker before the line count lists the session files, newest first, by when they started. Choosing one reads it back (`LogFiles.entries(in:)`), with the same filters. A line Paddock cannot read shows as text, and Clear stays off. Show File reveals the session's file. At launch, Paddock's logs last written over a week ago are removed (the earlier single `paddock.log` too); nothing else in the folder is touched. Crash analysis: PAD-16, PAD-17.
- **Ports** in each project's Info tab. Two directions:

  | | Global | Per sandbox (in sbx, the only store) |
  |---|---|---|
  | **Published** (sandbox to host, e.g. a dev server the agent starts) | `paddock.yaml` `ports.publishRange`, the host ports Paddock picks from (free in every sandbox); bind `127.0.0.1` | `sbx ports N --publish/--unpublish`; add, remove, copy URL |
  | **Host services** (sandbox to host loopback, e.g. Postgres on 5432) | sbx's own global rules (listed on the Network page, removable there; Paddock sandboxes deny them unless allowed) | Per-sandbox allow rules (`localhost:PORT`) |

  - Live state comes from `sandbox.ports` events and `sbx ports N --json`; a port published by hand with the CLI is simply in effect.
  - Docker API ports (2375/2376) and llmman's port cannot be added.
  - A project's `sbxenv.yaml` may publish ports (`ports:`, 127.0.0.1 only); sbx applies them at create, after the operator confirmed the file.
  - `paddock.yaml` has no host services: the only port setting is `ports.publishRange`.
- **Sheets:** New Project (folder picker, agent, clone mode, provider section, model picker from `/api/tags`, sandbox files ("Create sbxenv.yaml and a kit for this project", or a note that the folder has one), kits, extra folders with Read-only checked by default; checked when the project is made). The confirmation sheet for a project's `sbxenv.yaml` (backlog doc Project config file, Confirming). There is no Settings sheet: System > Edit Paddock's Config opens the app config in the default editor (a Settings window is PAD-12).
- **Per-project model activity:** not built yet (PAD-11): requests, tokens in and out, and errors from the gateway's metadata log.
- **Terminal:** SwiftTerm 1.20 (`TerminalView`) via SPM, fed by `SandboxShellSession`; the PTY is Paddock's own (`CPaddockPTY`, `posix_spawn`). SwiftTerm runs a build plugin (`SwiftTermBuildInfoPlugin`, writes its git commit into a generated file; reviewed): approve it once in Xcode (build, then Trust & Enable). Plugin validation stays on.

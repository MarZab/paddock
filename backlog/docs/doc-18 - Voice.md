Talk to an agent and hear it answer, with the agent as a full participant: it can speak, ask the operator something and get the spoken answer, and supply the words it works with so dictation of code names comes out right. Milestone M8 Voice.

**State (2026-10-29):** PaddockCore and the voice kit are written and tested on Linux (`VoiceTests`, `VoiceKitTests`; the kit's scripts run for real with Node). The app side (`App/Voice.swift`) builds on the Mac and dictation runs; the rest of the macOS behavior is checked in PAD-34. Not built: listening on its own after an agent speaks or asks (PAD-38), spoken state announcements in the app (PAD-39; the rule is `VoiceAnnouncements` in PaddockCore), stopping speech when the operator types, OpenCode's "prompt was spoken" note (PAD-34).

## Rules

- **Audio never enters a sandbox.** The Mac transcribes (SpeechAnalyzer with SpeechTranscriber, on-device) and speaks (AVSpeechSynthesizer). Only text crosses: what the operator chose to send, and what the agent wants spoken.
- **Paddock installs nothing.** The speech model for the Mac's language comes through macOS (`AssetInventory`) after the operator agrees in a dialog; better voices come from System Settings. macOS 26 only (the deployment target is 26).
- **The agent cannot open the microphone, and speaks only into an open popup** (PAD-101). A question opens the voice popup and waits for the operator; a say only goes to the conversation. An agent is read aloud only while its tab's popup is open; closing the popup cuts it off and drops what waits, and an agent outside a Paddock tab is never read aloud. The microphone is on only after the operator clicks it, the Listen pill, or Option-Space, until they pause, close, or Send; it shows red while on. The one exception is the operator's own: with Hands-free on, once an agent's say or question has been read out, the microphone opens for the reply, only while Paddock is the app in front and no other dictation is open.
- **Hands-free ends by itself** (PAD-38, `HandsFreeLimits`): only the operator turns it on (the pill, the microphone's menu; no message an agent can send is about it, tested), and it is not remembered across launches. It turns itself off, with a line in the Log (Voice), after 20 minutes without the operator speaking (the microphone's menu: Hands-free Turns Off, 5, 10, 20, 60 minutes, or Never; speech before a start word, a TV, does not count), and when Paddock goes to the background unless Keep On in the Background is chosen (off by default).
- **Text from the sandbox is untrusted** (like tab titles). `VoiceMessage` takes only its four kinds within the kit's limits (say 600 characters, question 300, 8 choices of 80, 200 words of 48 in letters, digits, spaces, and `. _ + # / ' -`, one line of 32 KB) and drops everything else. `SpokenText` cleans what is spoken: control, bidi, and zero-width characters dropped, code blocks removed, inline code, links, and emphasis reduced to their words, an address is "a link", a path only its last part, cut to 400 characters; plain text, never SSML. What is spoken is the cleaned text alone, with no project name before it (the operator's choice: who said it shows in the popup's conversation). A say older than 60 s when it arrives is not spoken. None of it decides anything.
- **Noise is not sent** (PAD-54): a dictation or typed answer goes to the agent only when it has a letter or digit and is not only fillers (uh, um, hmm, mm, ah, er, oh); leading punctuation is dropped (`DictationText.prompt`). So "." from the recognizer, or the comma left when a start word or command is taken out, is never sent, does not start hands-free's countdown, and leaves Send disabled; hands-free listens again as after a send.
- **Dictation is a paste.** `BracketedPaste` writes the text to the agent's PTY between the bracketed-paste markers with control characters dropped (so it cannot end the paste or send escape sequences), and submitted (Return) only when the operator clicks Send or hands-free sends it.

## Speaking (`SpeechQueue`)

One queue for the whole app: utterances never overlap. Each project may have 3 waiting; more are dropped. Push-to-talk in a tab, or answering a question aloud, stops and drops what that tab's agent says (`interrupt(tab:)`). While muted (`voiceMuted` in the app's defaults), nothing is spoken. The synthesizer is `SystemSpeech` (AVSpeechSynthesizer) with the voice `SpeechVoices.pick` chooses: the one the operator picked in the microphone's right-click menu (Voice: Automatic or any installed voice of the Mac's language, with its quality), else the best installed for the Mac's language (premium, then enhanced, then basic; its own region first; never a novelty voice). The list follows voices macOS installs while Paddock runs. When only basic voices are installed for the language, the popup (with voice reply on) says so, with Get Voices (System Settings, Accessibility; then Spoken Content, System voice, Manage Voices) and a close button that hides the hint for good; the menu has Get Better Voices too. Paddock downloads no voice itself. Better local models (Kokoro and others behind a loopback server the operator runs) are not used.

## Listening (`SpeechListener`)

SpeechAnalyzer with `SpeechTranscriber` (volatile results shown live, final ones kept) for the Mac's language, fed from `AVAudioEngine`'s input converted to the analyzer's format. Contextual strings (`AnalysisContext.contextualStrings[.general]`) are `VoiceKeywords.combined`: the agent's words first, then the project's file and folder names two levels deep (no hidden or build folders; at most 300 in all). Whether they help with SpeechTranscriber or only with DictationTranscriber is open (PAD-34). Nothing is recorded or kept.

## The voice kit (`VoiceKit`)

A builtin kit, `voice` (`needs = ["status"]`, not recommended: the operator chooses it per project). It installs:

- **`paddock-voice`** (Node; every agent image has it). Named `paddock-voice`, not `paddock voice`: `paddock` belongs to the browser kit, and this kit does not need it.

  | Command | What it does |
  |---|---|
  | `paddock-voice say TEXT` | Shows in the voice popup's conversation; read aloud while voice reply is on and the tab's popup is open |
  | `paddock-voice ask QUESTION [--choice X]... [--timeout S]` | Shows in the voice popup (choices as buttons), read aloud while voice reply is on, waits (default 300 s, 5 to 1800), prints `choice: X`, `answer: TEXT`, `dismissed`, or `timeout`; on timeout or a signal it takes the question back (`cancel`) |
  | `paddock-voice words add\|remove\|list\|clear` | The sandbox's words for recognition |

  The kit refuses what Paddock would drop (too long, bad words, repeated choices) with exit 2 and a reason. The agent may `say` and `ask` at any time; voice reply only decides whether Paddock reads them aloud. That is the whole interface: the agent learns from the prompt hook when the prompt was spoken and whether voice reply is on, so there is no status command.
- **Messages:** each is one JSON line in a file in `/tmp/paddock-voice/out`, named by time, id, and kind (so a question comes before its cancel), written whole (rename). **`paddock-voice-watch`** (sh) prints each once and removes it, and prints the words (`state/words.json`) at start and when they change, so a new Paddock gets them again. The app follows it like the other watchers (backlog doc Kits, Watchers). Fixture: `Fixtures/voice/watch.jsonl`, the kit's own output.
- **Back into the sandbox,** always with `sbx exec -i` and standard input: `--answer ID` (only for a question that is still pending, only in the answer shapes), `--dictated TAB` (what the operator dictated, just before the paste), `--set-status TAB` (`VoiceSettings`: voice (not muted) and voice reply, both required; voice reply is on for an agent only while its tab's popup is open (PAD-101); sent when an agent tab comes to the front the first time, to every such tab again when voice reply changes, and to a tab whose popup opens or closes; `say`, `ask`, and the hook read it).
- **Claude Code hook:** `UserPromptSubmit` runs `paddock-voice --hook claude`, merged into `~/.claude/settings.json` with the status kit's merge script. When the prompt contains the tab's dictation record (at most 15 minutes old, compared without case and extra spaces), it removes the record. It adds `additionalContext` when the prompt was spoken (it may have misheard words) and when **voice reply** is on (and voice not muted), for typed prompts too: end with a spoken summary of one or two sentences (`paddock-voice say`), or ask a decision with `paddock-voice ask`. A spoken prompt with voice reply off says to reply in the terminal as usual; a typed prompt with it off gets nothing. It prints nothing else and never fails. The input shape is from Claude Code's hook docs; a capture on the Mac is PAD-34.
- **Agent instructions:** short, from the agent's side: what it says or asks shows in the operator's voice popup and is read aloud while voice reply is on (the hook says which with each prompt); `say` one or two plain sentences (no code, paths, lists, or secrets), ending with one while voice reply is on; `ask` for decisions (what it prints); `words add` for names.

## In the app (`App/Voice.swift`, `VoiceModel`)

- **One popup for all of voice:** over an agent tab with the voice kit, at the bottom right, a microphone; click it, or press Option-Space while that tab is in front (a local key monitor: Paddock only, no Accessibility access), and the panel opens above it and stays open. A question opens it too; a say does not (it shows when the operator opens the popup). At the top it shows the **conversation** (`VoiceConversation`, in memory, the last 50 per project): the agent's lines on the left (questions in purple), what the operator sent on the right (dictation, answers, Dismissed), newest at the bottom; a popup shows its own tab's lines, the left half's also those of agents outside a tab Paddock opened. Below it, what is heard, live, in a text field (clicking into the text pauses the microphone, so it can be edited before it goes; Return there sends it like Send, Option-Return is a new line; PAD-55), three pills, Listen (the microphone: pause, or listen again and add to the text), Voice reply, and Hands-free, and Send, which sends the dictation record, then pastes and presses Return. The popup stays open, after Send and after a question is answered, until the operator closes it with its close button, which also drops what was said and not sent (a question still waiting keeps it open; Dismiss answers it). Open per terminal tab. The pills are also the microphone's right-click menu (Voice reply, Hands-free). **Hands-free** (`voiceHandsFree`, the operator's only; turning it on turns on voice reply too, turning it off leaves voice reply as it is): **Start word** (PAD-50): when hands-free opens the microphone into a tab on its own (after a send, after an agent's say, after a spoken stop) with nothing said yet, nothing it hears counts until the operator says a start word, "Paddock" or "computer" by default (`voiceWakeWord` in the app's defaults, a comma-separated list set with `defaults write`; an empty string turns it off; `WakeWords`, each phrase up to four words, matched without case or punctuation, and given to recognition as contextual strings). What follows the first one said is the dictation ("computer, run the tests" sends "run the tests"); until then the text field says "Say "Paddock" or "computer" to start", final results without the word are dropped, "stop" and "send" do nothing, and nothing counts down. Clicking Listen, Option-Space, answering a question, and a dictation that already holds words need no start word. **Waiting music** (PAD-53): quiet music while a hands-free agent works on what the operator said: only while the microphone waits for a start word, the tab's agent reports working (the status kit; without it there is none), and 3 s have passed, so a quick reply gets none; it fades out within a second or so when the start word is heard, the agent stops working, or the microphone goes off. Generated, not recorded (`WaitingMusic`: Cmaj7, Am7, Fmaj7, G an octave below middle C, 10 s each with slow swells, fading in over 3 s; after a minute the chords fade out over 20 s and a soft note every 8 s is left; under a fixed ceiling, well below speech), fed to an `AVAudioSourceNode` on the shared engine by `WaitingMusicRenderer` (atomics, no locks on the audio thread), and only with echo cancellation, so the recognizer does not hear it; it never turns the microphone on. Waiting Music in the microphone's menu (`voiceWaitingMusic`, on by default); nothing while muted. **Chimes** (PAD-52): hearing a start word plays macOS's Pop, and a spoken "stop" or "cancel" (while dictating, or over an agent being read aloud) plays Bottle (`NSSound`, outside the shared audio engine); nothing while muted. Send happens on its own 4 s after the operator stops talking, counted from the microphone's sound, not the text, which lags behind (`VoiceActivity`: a level 12 dB above the room's background, learned as it goes, is speech; any speech or new text starts the 4 s over; sending first waits for the transcription to finish), with the seconds left shown in the Hands-free pill itself; pausing or editing stops that for the dictation, and so does saying "stop" (or "cancel") as a sentence of its own, which is dropped from the text and pauses the microphone. A spoken "stop" or "cancel" (while dictating, or over an agent being read aloud) turns the microphone back on 2 s later, for the paused dictation or (Hands-free) the next reply; it does not count down to a send again until the operator speaks. Clicking Listen, Cancel, Send, or the close button decides instead: nothing comes back on by itself. Listening again arms it again. Saying "send" as a sentence of its own sends at once, with or without Hands-free (`DictationCommand`: only a sentence that is nothing but the word counts, so "stop the server" and "send it to staging" stay text; the last command said wins). With Hands-free on the microphone stays on and follows the conversation, unless the operator turned Listen off (the pill, the microphone, or Option-Space; PAD-51): then nothing turns it on by itself, not after a reply, a send, or a question, and it does not listen for "stop" while an agent speaks, until they listen again or turn Hands-free on. after each send it listens again for the same tab (after an answer, for the question's tab); after an agent's say has been read out it listens for the reply into its tab, and after a question for the answer. While an agent is read aloud the dictation pauses (what it heard so far stays), so it never takes the Mac's voice for the operator's, and listens again afterwards. Meanwhile (with Hands-free on, or when a dictation was listening) the microphone listens only for "stop" or "cancel": it hears the speaker too, so the word comes mixed into the agent's words and only in tentative results, and either word anywhere in one counts unless the agent's own text has it (`DictationCommand.stopsSpeech`). It cuts the speech off; everything else it hears then is dropped. The popup shows what it hears meanwhile (an ear and "Hearing: ..."), the log says when it could not start or heard nothing. **Echo cancellation** (`VoiceAudio`, PAD-46): while the microphone is on, it and the speech share one AVAudioEngine; the microphone runs with Apple's voice processing (other apps' sound is not ducked; the engine's output uses the microphone's format, which voice processing requires, -10875 otherwise; if it still will not start, the microphone works without it and the log says so), and the speech is rendered with AVSpeechSynthesizer.write and played through a player node on that engine, so it is taken out of what the microphone hears and the operator can talk over it. With the microphone off, speech plays through AVSpeechSynthesizer as before and the microphone stays off. The popup's Send button turns into Cancel while an agent is read aloud and does the same as saying it; a dictation that already holds words is resumed rather than replaced. The first use asks to download the speech model when macOS has none for the language.
- **Voice reply:** the operator's pill (`voiceReply`). It decides only what is read aloud: on (and not muted), what agents say and ask into an open popup is spoken, and the hook asks them to end with a spoken summary; off, it shows in the popup only and they reply in the terminal as usual.
- **Questions:** an agent's question opens the same popup by itself, over its tab (or over the left half's terminal when its tab is not shown, a shell tab too): the question, its choices as buttons, a field to type an answer, the pills, Dismiss, and Send. Listen (or Option-Space, or the microphone) answers aloud (`VoiceAnswer.to`: a choice by name or place, "the second one", "option 3", "last", else the words). The question is also spoken when its popup was already open; with Hands-free on, the microphone opens once it has been read out and the answer goes 4 s after the operator stops talking ("stop" holds it). A question goes when answered, taken back, or its sandbox stops.
- **Not yet:** a menu for mute (an app default, `voiceMuted`, settable with `defaults write`), listening on its own after an agent speaks or asks (PAD-38), state announcements (PAD-39), a notification for a question from a project in the background (PAD-37), stopping speech when the operator types.

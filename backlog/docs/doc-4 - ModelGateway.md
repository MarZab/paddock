A small HTTP reverse proxy inside Paddock, the **only** path from a sandbox to a model.

- **Listeners:** one per project on `127.0.0.1:<port>`, the port taken from `paddock.yaml` `models.gatewayPorts` (default `[17480, 17579]`) and stored in the project's file (`gatewayPort`), since the sandbox is created with it. Never a wildcard or LAN address. All listeners share one upstream client. Built on SwiftNIO (`NIOHTTP1`) with AsyncHTTPClient for the upstream call; both are added as package dependencies of PaddockCore.
- **Upstream:** only `http://127.0.0.1:17434` (llmman). The gateway never forwards anywhere else.
- **Routes (allowlist; everything else is `403`):** `POST /v1/messages`, `POST /v1/messages/count_tokens`, `POST /v1/chat/completions`, `POST /v1/responses`, `GET /v1/models` (answered by the gateway with the project's one model). No `/api/*`, `/llmman/*`, `/props`, `/metrics`, or web UI paths.
- **Project identity is the port, not a token:** sbx's per-sandbox HTTP rule lets a sandbox reach only its own project's gateway port, so the port a request arrives on says which project sent it. There are no gateway tokens, no Keychain, and no key management; agents present a fixed dummy key (`paddock`), which the gateway ignores and strips. Guards: two projects never share a port (project file validation), no `sbxenv.yaml` port, kit host, or host rule may name any gateway port, and when a global rule reaches the gateway ports (such as `localhost` or `**`), the other projects' gateway ports are denied explicitly. A token would add nothing against other host processes, because llmman itself is open on loopback without a key.
- **Model pinning:** the gateway rewrites the request's `model` field to the project's model, so an agent cannot load other models or trigger a pull of a model name it chose. Paddock only starts a project when its model is already in llmman's store (`/api/tags`); downloads happen in llmman's UI, by the operator.
- **Limits:** request body size cap (default 32 MB, `413`), per-project concurrency cap (`429`), a 30-minute upstream timeout for long generations, and a 5-second connect timeout with no connection retries, so a stopped llmman is an immediate `502` instead of a request that hangs until the generation deadline (AsyncHTTPClient retries refused connections by default). Hop-by-hop headers and the incoming `Authorization` / `x-api-key` are stripped before forwarding.
- **Streaming:** SSE responses pass through unbuffered.
- **Logging:** metadata only (time, project, route, status, bytes, duration, and model token usage from the response's `usage`), kept in memory by the app (`AppModel.gatewayLog`, the last 500). No view shows it yet: the log drawer and per-project activity are PAD-11. Never request or response bodies.
- **Second layer in sbx:** sbx policy rules support HTTP method and path filters (`--method`, `--path`). Each Paddock sandbox gets `sbx policy allow network --sandbox N localhost:<its gatewayPort> --method POST,GET --path '/v1/**'` and `--deny-network localhost:17434`, so even a gateway bug cannot expose llmman. The rule is also how Paddock reads a sandbox's port back (`PolicyPlanner.gatewayPort(ofSandbox:)`).

**Wiring an agent to the gateway (instead of `--model`):**

How sbx does it (M0 round 5): `--model` writes a **mixin kit** (`schemaVersion: "1"`, `kind: mixin`, `requires: {agent: ...}`) under sbx's `model-kits/` folder that sets environment variables, adds `network.allowedDomains: ["localhost:17434"]`, and (for Claude) runs one install command. Paddock copies the environment and install parts and replaces the network part with its own per-sandbox rules.

- **Claude Code:** environment only, at create; there is no gateway kit since PAD-73.2. `sbx create --name N -e ANTHROPIC_BASE_URL=http://host.docker.internal:<gatewayPort> -e ANTHROPIC_AUTH_TOKEN=paddock -e SBX_CRED_ANTHROPIC_MODE=none -e CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1 -e CLAUDE_CODE_AUTO_MODE_SERVER=0 -e CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS=1` plus every model variable set to M (`ANTHROPIC_MODEL`, `ANTHROPIC_SMALL_FAST_MODEL`, `ANTHROPIC_DEFAULT_OPUS_MODEL`, `ANTHROPIC_DEFAULT_SONNET_MODEL`, `ANTHROPIC_DEFAULT_HAIKU_MODEL`, `CLAUDE_CODE_SUBAGENT_MODEL`), then `claude FOLDER` (`ClaudeGateway`, `AgentLaunchPlanner.create`). The dummy credential is a token, not an API key: Claude Code sends `ANTHROPIC_AUTH_TOKEN` as `Authorization` without the approval it asks for a custom `ANTHROPIC_API_KEY`. sbx 0.51's own claude kit already marks onboarding complete. `SBX_CRED_ANTHROPIC_MODE=none` keeps sbx from writing an `apiKeyHelper` as well. The gateway drops every auth header (`GatewayPolicy.forwardedHeaders`). Checked with `mise run m0 kits` (2026-11-04, sbx 0.51.0): `claude -p` in a sandbox with no kit answered through a stand-in gateway, which got `Authorization` and no `x-api-key`. Claude warns that claude.ai connectors are disabled while a token is set.
- **OpenCode:** sbx 0.51's own opencode agent is a v3 kit (`docker.io/sbx/opencode`) that ships OpenCode 2 (2.0.29 in the PAD-73.2 capture), so Paddock no longer adds a kit to replace OpenCode 1. Its opencode kit is gone, and projects that chose it drop it (`KitSelection.removed`). Not checked with 2.0.29: the config details below were checked with 2.1.4. For the gateway: one `-e OPENCODE_CONFIG_CONTENT=...` built by Paddock, mirroring sbx's: `{"$schema":"https://opencode.ai/config.json","model":"paddock/M","enabled_providers":["paddock"],"provider":{"paddock":{"name":"paddock","npm":"@ai-sdk/openai-compatible","options":{"baseURL":"http://host.docker.internal:<gatewayPort>/v1","apiKey":"paddock"},"models":{"M":{"name":"M"}}}}}`, plus `SBX_CRED_ANTHROPIC_MODE=none` and `SBX_CRED_OPENAI_MODE=none`. `enabled_providers` is Paddock's addition: without it OpenCode lists its own free models (`opencode/*`) and every provider it finds a key for next to the gateway's model; with it, `opencode models` lists only `paddock/M` (checked with 2.1.4, 2026-10-24; `disabled_providers` and `OPENCODE_DISABLE_FREE_MODELS` hide only the free models). OpenCode 2 keeps a background server (`opencode serve --service`) that holds the config it started with. So Paddock also writes the same config to `~/.config/opencode/opencode.json` in the sandbox (`sbx exec`, base64 in argv: no secret, only the dummy key), after create and before each agent session; when the file changed, it runs `opencode service stop`, and the next session starts the server with the new config (checked with 2.1.4: a server started without the config lists every provider; after the script, only `paddock/M`). 2.1.4 reads `opencode.json` there, not `config.json`. sbx's version also adds `variants` (thinking on or off through `chat_template_kwargs.enable_thinking`); Paddock does not copy them yet (PAD-5).
- **Seen once:** a sandbox's gateway rule (added with `sbx policy allow` after create) was missing later, cause unknown; it survives `sbx stop`. The trial checks the rule after create and re-adds it on reuse with a warning; in the app, Sync lists a missing gateway rule under Needs attention with Apply (doc: App config, Sync; automatic re-apply is PAD-20).
- **Trial without the app:** `mise run gateway --model M [--agent opencode]` (`Sources/paddock-gateway`, workspace `scratch/trial` in the repo, gitignored) runs the gateway against the real llmman and creates one sandbox wired exactly as above (FolderPolicy, PolicyPlanner denies, kit, HTTP rule). Run it again to reuse the sandbox: the port is read back from its HTTP rule.
- **Agent default** (no local model): no gateway, no extra variables; the agent uses its default provider through its own account (e.g. Claude Code with Anthropic, through sbx's normal credential injection).



## Who may call (PAD-82, PAD-88)

`GatewayPolicy.decide` refuses, with 403 and before routing, a request whose `Host` header names anything but `127.0.0.1`, `localhost`, `[::1]` or `host.docker.internal` (a request without `Host`, which a browser never sends, is judged by the other rules), and any request with an `Origin` header. Agents and sbx's proxy send no `Origin`. Tests: `GatewayPolicyTests`. `ModelGateway.Configuration.maxConnections` (32) closes a connection over the limit at once; a 429 and a 413 are logged like any other answer. Still open: an idle or read timeout on inbound connections (a limit that does not end a long generation needs the request phase tracked; PAD-88).

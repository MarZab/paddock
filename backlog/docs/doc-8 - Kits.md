sbx kits add tools and settings to a sandbox at create (`sbx create --kit REF`, repeatable). **Paddock's own kits are v3 kits (PAD-73.2):** a folder in `<config>/kits/` named `paddock-<kit>` with `<folder>.yaml`. sbx names a local kit after its folder, and names in one sandbox must differ: sbx 0.51 ships an `opencode` kit of its own. (`KitFile`; the `spec.yaml` of the earlier v1/v2 kits is removed when Paddock writes the kit). Each one is a `kind: mixin` with `version` and `provides` (sbx refuses a `provides` without a version) and capabilities, not top-level sections:
  - Environment is set through `args` with `env` (v3 has no environment section).
  - Network goes in `network-policy@2`, and the dashboard's port in `port@1`.
  - Install and startup steps go in `lifecycle@1`. An install step sees only the environment it names (`env: [PATH, HOME, HTTP_PROXY, ...]`), so paths are written out (`/home/agent`). Anything that needs `WORKSPACE_DIR` runs at start, since it exists only in the running sandbox.
  - Agent instructions go in `agent-context@1`. sbx's own claude and playwright kits use @1, and sbx refuses to compose @1 with @2.

  They pass `kit.schema.json` (checked with `PADDOCK_DUMP_KITS`). Not yet run on the Mac: `mise run m0 kits` creates a claude and an opencode sandbox with them. Paddock lets the operator choose **mixin** kits per project (`Config/Kits.swift`, `KitSelection`):

- **Defined only in `paddock.yaml`**, as entries under `kits:` (`source` = anything `--kit` takes: an image reference, `git+https://`, or an absolute local path; or `builtin` = one of Paddock's own; plus `summary`, `recommended`, `agents` = agent kinds, `needs` = kits it builds on). A kit runs install steps in the sandbox and adds its own network rules (sbx marks them `provisioned`), so these are the only kits Paddock adds itself. A project's own `sbxenv.yaml` names sbx's catalog kits and its own local kits, confirmed with the file (backlog doc Project config file). A local kit inside any project folder is refused (an agent could rewrite its steps and rules). Sources may not start with `-` or contain whitespace.
- **Defaults** (`AppConfig.defaultKits`, merged with the file; `enabled = false` removes one, a section without `source` changes one): `status` (recommended for every agent; see Agent status below), `browser` (needs `playwright`), `voice` (needs `status`, not recommended: opt-in per project; backlog doc Voice), and two of sbx's kits: `playwright` (`docker.io/sbx/playwright:1.61.1`, pinned by digest) and `mise` (`docker.io/sbx/mise:2026.5.2`, pinned by digest; offered for every agent but not recommended, so off until chosen; PAD-75). The `setup` kit is gone (PAD-73.3): Paddock writes a project's files itself. So are the `opencode` kit (sbx 0.51's own opencode kit ships OpenCode 2) and the gateway kit (environment does it; backlog doc ModelGateway), both PAD-73.2. Paddock ships a kit only where sbx has nothing for the job. **`node`** (`NodeKit`) is new for that reason: sbx 0.51's agent images have no Node, yet `status`, `voice`, `browser`, and sbx's own `playwright` run on it ("npm: not found", "env: 'node'" without it). No kit of sbx's or Docker's provides Node, so this one copies `node`, `npm`, and `npx` from `node:26.13.0-bookworm-slim` (Node 26 LTS, the bookworm build for its older glibc), pinned by digest, in a `FROM scratch` recipe (`paddock-node.dockerfile`, which sbx builds at create). `status`, `browser`, and `playwright` need it, so it is selected with them. A project that chose it drops it (`KitSelection.removed`). Any other kit is a section of its own: **an entry without `source` names sbx's contrib kit** (`gh:` is `docker.io/sbx/gh`, the v3 build, following `latest`; set `source` with a tag and digest to pin it). From sbx 0.51 the built-in agents are v3 kits themselves (`claude` is `docker.io/sbx/claude`), and v1/v2 kits (the `-kit` builds) no longer combine with them (PAD-73.2). Worth knowing before adding one (research 2026-10-25): `claude-model-runner` bypasses the gateway, `code-server` and `claude-mem` listen unauthenticated on `0.0.0.0`, `panw-*` ship telemetry off the sandbox, `grafana` and `dynatrace` override `NO_PROXY`, `snyk-evo-ads` and `kernel` rely on `**.` wildcards sbx does not enforce yet, and `gitlab` needs `sbx secret set gitlab` before a create.
- **Adding from the interface:** the kit picker has a field that takes a contrib kit's name or anything `--kit` takes (`Kit.parseInput`; the name comes from the reference's last path part without `-kit`, a tag, or a digest) and adds `NAME:` under `kits:` in `paddock.yaml` (`AppConfigFile.addKit`, checked like a hand edit before it is written), then selects it. A defined kit's name only selects it. A new `paddock.yaml` (Edit Config or the first added kit) starts as `AppConfigFile.template`: every section with its defaults and what each key does, commented out.
- **Choosing:** the New Project sheet lists the kits offered for the agent, preselected from `recommended`; selecting a kit selects what it needs, unselecting one unselects what builds on it. There is no gateway kit (PAD-73.2): a local model is environment at create (backlog doc ModelGateway). A project's chosen kits get what they need added (`Project.chosenKits`), so a kit that gained a need still works for a project that chose it before. The Info tab's Kits row edits the choice later (`AppModel.setKits`).
- **Order:** each kit after the kits it needs, otherwise by name. v3 composition: the workload's install steps run first, then each mixin's in order, network allows add up per phase (deny wins), and sbx lists every kit's hosts as one `kit:<sandbox>` rule (backlog doc M0 findings).
- **Project file:** `kits` (the operator's choice; files from before kits get what Paddock always added, `KitSelection.legacy`) and `sandboxKits` (the `--kit` values the sandbox was created with; sbx does not report them). A difference is a "recreate" item under Needs attention; kits that no longer resolve show as a problem and stop a create or recreate before anything is removed.
- **Not yet:** the confirmation sheet does not show a kit's hosts before create (PAD-7); they show after create as "agent kit" rules on the Network page. Kit arguments (`--kit-arg`) are not supported (PAD-8).

## Agent status (PAD-23)

The `status` kit (`AgentStatusKit`) makes each agent report whether it is **working**, **waiting** on the operator, **idle**, or **ended**. There is no standard across agents (research 2026-10-25), so the kit installs each agent's own signal, and both call `paddock-agent-state STATE [claude|opencode] [SESSION]`. It writes **one file per agent session**, `/tmp/paddock-agent/sessions/<session>.json`: `{"session","state","agent","tab","pid","time"}`, atomically, only when the state or the agent's process changed (`time` is when the state began), printing nothing and never failing. `pid` is the agent's process: the first parent of the script that is not a shell (`sh`, `dash`, `bash`, `zsh`, `ash`, `busybox`, `env`, `timeout`; the hook's `sh -c`, say), 0 when there is none (PAD-64). The session is Claude Code's `session_id` (read from the hook's stdin) or the third argument. The **tab** is `$PADDOCK_TAB`: the app opens an agent tab with `sbx run --name N -e PADDOCK_TAB=<tab id>` (`SandboxShellSession.sandboxEnvironment`; `-e` applies to the agent session and so to a re-attach), so two tabs of one sandbox report apart. A shell tab gets it too, as `sbx exec -it N env PADDOCK_TAB=<tab id> bash`, so an agent the operator starts in the shell reports that tab (PAD-64). `paddock-agent-watch` prints each session's line when it changes (all of them once at start; an ended session once, then its file is removed; a session whose `pid` is no longer in `/proc` is printed once as ended and removed too, so an agent killed or closed without a `SessionEnd` goes (PAD-64); a file untouched for a day is dropped). The app follows it with `sbx exec SANDBOX sh -c ... paddock-agent-watch` (see Watchers), reads each line with `AgentState(line:)` (drops anything but a known state, an ID of letters, digits, `-`, `_` up to 64, a non-negative time, at most 512 bytes), and keeps them in `AgentStates`, whose `state(ofTab:)` is what a tab shows. The state is display-only: it is never used for rules, mounts, or any other decision.

**Display** (`AgentActivity`: none, working, waiting; `activity(ofTab:)` for a tab): one `paddock-agent-watch` per running project with the kit (`AppModel.syncAgentWatchers`, started again with a growing delay when it ends). Across a restart the marks stay as they were: the new watcher prints every session at once, and 3 s after its first line the sessions it did not report are dropped (`AgentStates.beginResync`/`endResync`, PAD-61); a watcher that reports nothing forgets everything. Each end of a watcher that had reported is logged (Sandbox activity, with how long it ran), to find what ends it. Each agent tab shows its newest session's state (`AgentTabMarks`; "finished" goes when the operator looks at the tab, which counts only while its project is shown and Paddock is active), and so does a shell tab an agent reports from. The sidebar lists the agents under their project, each with its own mark (`SidebarAgents`, backlog doc UI, Agents in the sidebar); the project's own mark shows only its sandbox's state and approval requests (PAD-63). A stopped sandbox shows no agent state. Nothing pulses (PAD-33: a pulse had to be watched to be read).

- **Claude Code** (hooks, code.claude.com/docs/en/hooks), merged into `~/.claude/settings.json` by a Node step (see Node scripts) that keeps existing hooks and adds each of ours once; a settings file it cannot parse is left alone. `UserPromptSubmit`, `PostToolUse`, `PostToolUseFailure`, `PermissionDenied` and `PreToolUse` (any tool but the two below) set working; `PermissionRequest`, and `PreToolUse` of `AskUserQuestion` or `ExitPlanMode`, and `Notification` of `elicitation_dialog` or `elicitation_url_dialog`, set waiting; `SessionStart`, `Stop` and `StopFailure` set idle; `SessionEnd` sets ended. `PermissionRequest` is used rather than the `permission_prompt` notification, which fires only after about six seconds. A hook has a 5 s timeout and prints nothing.
- **OpenCode** (plugin, opencode.ai/docs/plugins): `~/.config/opencode/plugins/paddock-status.js` on the `event` hook. Busy sessions (`session.status` busy or retry) and sessions with a pending `permission.asked`, `permission.updated`, or `question.asked` are tracked by session ID, so a child session going idle does not hide its parent; waiting beats working beats idle. The plugin reports one entry per OpenCode process (`oc-<PADDOCK_TAB>`, or its pid), not one per session. OpenCode 2's background server is shared, so tabs of one sandbox may share an entry (to check). OpenCode has no exit event, so it never reports ended.
- **Tested** here: the state script, the settings merge, and the plugin (with Node) run for real in `AgentStatusKitTests`.
- **Not yet checked on the Mac (PAD-23):** that sbx leaves `~/.claude/settings.json` and the plugin directory alone at agent start; that `PermissionRequest` and `AskUserQuestion` fire as the spec says in the Claude Code version sbx ships; that OpenCode 2.1.4 (`@opencode/cli`) loads plugins from that directory and sends the events of the 1.x SDK types (`session.status`, `permission.asked`, `question.asked`); a Stop while background tasks still run reads as idle. A Claude Code process that dies without a `SessionEnd` leaves its last state until the day-old cleanup. The app does not follow the watcher yet and the tab and sidebar views are not built.

## Watchers (PAD-30)

The app follows up to three long-running watchers per running sandbox, `paddock-agent-watch` (this kit), `paddock-browser-watch` (the browser kit, backlog doc Browser), and `paddock-voice-watch` (the voice kit, backlog doc Voice), each through `sbx exec`. Ending the `sbx exec` on the Mac does not end its watcher in the sandbox, and a Paddock that crashes ends neither, so before PAD-30 every restart left another pair in each sandbox (six of each, about 75 MB per browser watcher, in one capture). Now:

- **A watcher ends when Paddock is gone.** The app runs `sbx exec -i SANDBOX sh -c SCRIPT paddock-watch WATCHER` with standard input a pipe it holds open and never writes (`FoundationLineStreamer(holdsInputOpen:)`). The kernel closes it when Paddock quits, crashes, or is killed, and `sbx exec -i` passes the end of input into the sandbox (checked on the Mac 2026-10-28: killing the client closed stdin inside within a second). The script runs the watcher with empty input and a `cat` on the real input (kept on fd 3, since a background job's input is /dev/null); when that `cat` ends, it stops the watcher. A watcher that ends by itself ends the script with its status, so the app starts it again as before.
- **Each start replaces older ones.** First the script stops every process in the sandbox whose command line is exactly `node /usr/local/bin/WATCHER`, an absolute `.../node /usr/local/bin/WATCHER` (a Node watcher started through `NodeScript.header`), or `/bin/sh /usr/local/bin/WATCHER`. The browser kit's one-off `paddock-browser-watch --captured ...` calls have arguments, so they are left alone. Each app tags its watchers: the script runs `WATCHER --for=BUNDLE_ID` (`SandboxWatchers.owner`, the app's bundle ID; the watchers ignore the argument) and stops only watchers with its own tag or no tag (from before PAD-61), so Paddock and Paddock Dev following one sandbox no longer stop each other's watcher in turn (which blanked and restored the agent marks every few seconds). It needs only sh, tr, cat, and kill, so it works with every kit version without recreating a sandbox.
- **Quitting ends the streams on the Mac.** Every `FoundationLineStreamer` process is tracked, and the app's `willTerminate` ends them all (`FoundationLineStreamer.terminateAll`): watchers and `sbx events`. `sbx exec` took a few seconds to exit after SIGTERM in one check.
- **Launch stops Mac-side leftovers.** Once sbx answers, `SandboxWatchers.stopLeftovers` reads the Mac's process list (`HostProcesses`, `ps -axww -o pid,ppid,user,rss,%cpu,etime,command`) and sends SIGTERM to the current user's processes whose parent is gone and whose command is exactly a watcher's `sbx exec` (with or without `-i`, or the earlier `sbx exec SANDBOX WATCHER`), and logs how many. Nothing else is touched; other orphaned sbx tools are PAD-31's.
- **Signals reach children.** A child inherits the signal mask of the thread that starts it, and Swift's worker threads block nearly every signal (Linux's libdispatch; Foundation there passes the mask on), so a streamed process ignored `terminate()`. Both runners start processes with `Process.runUnmasked()`: the whole mask is cleared on macOS (Foundation follows exits through kqueue); on Linux, where only the tests run, SIGCHLD stays blocked, since Foundation follows exits through it there, and the tests start shells that wait for children through a small python3 step that clears it. The PTY terminals already reset the mask in `pty.c`.
- **Not yet checked on the Mac (PAD-30):** that quitting and a crash (`kill -9`) leave no watcher in the sandbox and no `sbx exec ... paddock-*-watch` on the Mac.

## Node scripts (PAD-60)

Paddock's Node scripts in a sandbox (`paddock-voice`, the browser kit's `paddock` and `paddock-browser-watch`, and the Claude Code settings merge the install steps run) do not depend on what the project's image puts on PATH as `node`. The image is the project's business: a version manager's shim there may fail for the project folder (mise trying to install a node version it cannot), and Paddock sets no version-manager variables and runs no version-manager commands. Instead each script starts with `NodeScript.header`, a `/bin/sh` script whose second line is also JavaScript (a string and a comment to Node): it tries each `node` on PATH, then `/usr/local/bin/node` and `/usr/bin/node`, and runs the script with the first that starts (`node -e 0`, stdin left for the script); with none, it says so and exits 127. The install steps run the merge with `sh FILE`. A watcher started this way runs as an absolute node and its path, which the watcher replacement matches as well. Sandboxes created before this keep their old scripts until they are recreated.

## Project setup (removed)

The `setup` kit taught agents Paddock's earlier project file and project Dockerfiles. It was removed in PAD-73.3: Paddock writes a project's `sbxenv.yaml` and kit itself (`SandboxFiles`, backlog doc Project config file), with its rules as comments in them.

## Adding a kit

The kit field (New Project, Edit Kits) takes a contrib kit's name (`mise`) or anything `--kit` takes. One of sbx's catalog kits (a name, or `docker.io/sbx/...`) goes to the project's `sbxenv.yaml` `kits:` when the project has one (`ProjectKitFile`; the file then needs a confirmation and a recreate), so the file stays the whole setup for `sbx env run`. Anything else, and any kit for a project without the file, is added to paddock.yaml under `kits:` (`AppConfigFile.addKit`) and selected.

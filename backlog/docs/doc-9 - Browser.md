The agent tests web apps in a real browser, and the operator watches. Everything runs in the project's one sandbox; nothing is a second sandbox.

- **Kits:** sbx's `playwright` kit brings Chromium's system libraries and `/opt/ms-playwright` (and scripted tests: `npx playwright test`). Paddock's `browser` kit (`BrowserKit`, schema v2, `needs = ["playwright"]`) adds Microsoft's `@playwright/cli` (pinned), the Chromium build it was made for, and its skill for Claude Code and `~/.agents/skills` (OpenCode), so any agent with a shell can drive it. `PLAYWRIGHT_MCP_BROWSER=chromium`, since playwright-cli otherwise asks for Google Chrome (no Linux arm64 build). Its `agentInstructions` tell the agent to use named sessions for anything the operator should see.
- **HTTPS and files:** sbx's proxy re-signs HTTPS with its CA (`/usr/local/share/ca-certificates/proxy-ca.crt`), and Chromium on Linux checks only its own store, so every external site failed with `ERR_CERT_AUTHORITY_INVALID`. The kit installs `libnss3-tools` and imports the CA into `~/.pki/nssdb` on every start (certificate checks stay on; never `ignoreHTTPSErrors`). `PLAYWRIGHT_MCP_OUTPUT_DIR=/tmp/playwright-cli` keeps playwright-cli's snapshots and logs out of the project.
- **Dashboard:** the kit's `setup.startup` runs the real `playwright-cli show --port 38323 --host 0.0.0.0` on every sandbox start, and its `ports` entry makes sbx publish 38323 on `127.0.0.1` (a random host port). Not 9323: that is `npx playwright show-report`'s default, and a report server there once took the dashboard's place, so every browser tab showed the report. The agent instructions say the port is Paddock's, and the browser tab checks what answers on the port (`BrowserKit.dashboardAnswer`): the dashboard (`/` redirects to `/index.html?ws=...`), another server (it says so), or nothing, when Paddock starts the dashboard itself once (`sbx exec`, `BrowserKit.startDashboardScript`, the same command as the kit's startup step) and offers Start Dashboard. The command has no `pgrep` check: `pgrep -f 'playwright-cli show'` matched its own `sh -c`, so the kit's startup never started the dashboard; the dashboard is a singleton, so a second start just exits. The tab's header shows the page's own URL. It lists every session in the sandbox with all their tabs, keeps one selected page per connection (a click in one view's session list changes only that view), streams it live, and lets the operator take over mouse and keyboard. (`playwright-cli -s=NAME show` would switch every connected view at once, so Paddock never uses it.)
- **The agent** uses playwright-cli as it always would: its own sessions and tabs. Its `agentInstructions` say the operator sees every page live in Paddock and picks what to look at, to name sessions by purpose, to tell the operator the session and page it means (after checking a screenshot), to close what it is done with, and that servers on localhost are fine (the browser runs in the same sandbox).
- **Following it** (`BrowserActivity`): the kit links the real CLI to `/usr/local/lib/paddock-browser/playwright-cli` and puts a wrapper (sh) under every `playwright-cli` name on the PATH. The wrapper notes each command's session (`-s NAME`, `-s=NAME`, `--session`, `PLAYWRIGHT_CLI_SESSION`, else `default`; only letters, digits, `.`, `_`, `-`) with `start` and `end` in `/tmp/paddock-browser/events`, then runs the real CLI with the same arguments and exit status; commands that act on no session (`show`, `list`, `install`, `close-all`, ...) are not noted. The watcher (`paddock-browser-watch`, Node) prints JSON lines: `tabs` (every open session's tabs, from `list --all --json` and each session's `tab-list --json` run in its workspace folder; a session belongs to the workspace of the nearest folder with `.playwright`, which `playwright-cli install` creates in a project, or to the global one, and plain `list` shows only the current workspace's sessions, which is why tabs from a project's workspace once never appeared; two sessions of the same name in different workspaces show as the first, after each command and every 5 s, only when they changed), `busy` and `idle` per session.
- **Tabs:** while a project with the browser kit runs, Paddock follows `sbx exec N paddock-browser-watch` (restarted with a growing delay when it ends; each start first stops older watchers in the sandbox, and quitting ends it: backlog doc Kits, Watchers). Two kinds of host tabs, mixed with the terminal tabs in one order (`TerminalTabs.arranged`), alike in design and told apart by color; none ever takes the operator's focus (a new one gets a dot):
  - **Playwright** (green, one per project): the whole dashboard, the agent's sessions with their own tabs, once the agent has a session of its own. Its icon pulses while the agent runs a command, and a dot marks changes the operator has not seen. Closing it hides it until the next change. Pages the operator closes inside the dashboard are noted for the agent (the watcher sees a page vanish with no command from the agent in the last 3 s: "Paddock: the operator closed a tab ... in the dashboard").
  - **Show tabs**, one per `paddock` call (`BrowserShow`): the agent shows a URL or a file (`--title`, `--note`; at most 12). By default the content renders in the sandbox, as a page of the `paddock` playwright-cli session (the only session with `file:` access, `PLAYWRIGHT_MCP_ALLOW_UNRESTRICTED_FILE_ACCESS`), shown in a dashboard view trimmed to the page (`BrowserActivity.showScript`: hides `.split-view-sidebar`, selects the page; depends on the dashboard's markup like the selection); accent color. With `--native` (the agent asks for it, and should say why in its note) a file renders on the operator's Mac (`NativeShowPolicy`): orange, and nothing loads until the operator opens the tab, so they can dismiss it unseen. Text renders natively (SwiftUI). Markdown (`.md`, `.markdown`) renders as Paddock's own page (`MarkdownPage`, swift-markdown with cmark-gfm: tables that scroll sideways, task lists, code, light and dark), in the same web view with JavaScript off: front matter shows as a key/value block, raw HTML as literal text, smart quotes stay off, bare http(s) URLs become links, and a table row with one cell too many because of an unspaced pipe (`"0"|"1"`) keeps the pipe as text; relative images and links to files beside it load through the tab's scheme (a linked `.md` renders too), `#anchors` reach headings, other links do nothing. A Rendered/Source switch at the top right shows the file as it is (kept per tab while Paddock runs). Anything else renders in a web view that keeps no data and loads only `paddock-file://<id>/<path>`, each file read through `sbx exec paddock --read ID PATH` (only the shown file or one beside it, checked in the sandbox by real path and in Paddock; at most 20 MB), with content rules blocking every other load. Opening, closing, and dismissing a show tab are told to the sandbox (`--operator ID opened|closed|dismissed`; closing also closes its page), and the agent reads them with `paddock status ID`.
- **Handles, not identities** (several agents in one project share the sandbox, its playwright-cli registry, the dashboard, and `paddock`'s state): every session and shown tab is reached only through the name or id the tool gave out. The wrapper makes `open` always start a new session named after the agent's suggestion plus a random suffix (`counter-7f3a`, kept in `/tmp/paddock-browser/sessions`) and says so; every other command needs `-s` with such a name (no `default` session, `PLAYWRIGHT_CLI_SESSION` ignored), and `close-all`/`kill-all` are refused. `paddock` ids are `tab-` plus four random hex digits, claimed exclusively (`open(..., 'wx')`); the `paddock-tabs` session changes under a lock (a directory, taken over after 30 s) and keeps the URL playwright-cli reports for the page it opened (checked with four calls at once). What the operator did with a tab is kept in its record (`paddock status ID`; tabs closed by anyone move to `/tmp/paddock/gone`), and notes about the agent's own sessions stay per session, so each agent hears only about its own. There is no list of tabs. An agent that loses its handles opens new ones; the old ones stay until the operator closes them. (This replaced giving each agent tab an identity through `sbx run -e`, which works per session but is not needed.)
- **Tab menus, no status bar:** browser and show tabs show only their content (title and note are in the tab's tooltip). Their context menus have Refresh (the Playwright tab reloads its dashboard view; a page shown in the sandbox reloads there; a native tab reads its files again) and Back for show tabs (in the sandbox: `--operator ID back`, which keeps the URL the page lands on; Paddock also finds a show's page by its place among the page shows; native: the web view's history). The dashboard's own Back needs take-over mode, so the Playwright tab has no Back. The agent has the same on its own tabs: `paddock reload ID`, `back ID`, `goto ID URL-or-FILE` (the operator's go through `--operator ID reload|back`, so the history says who); a native tab gets a revision, raised by the agent's reload or goto, and an open one loads again.
- **Captures and annotations reach the agent.** The dashboard's Save screenshot and Record video end in a download in the viewer (checked in its source: a PNG with an accessibility snapshot; a webm streamed from the sandbox and deleted there). Paddock's dashboard web views catch the download into a temporary file and hand it to the sandbox instead (`BrowserCapture`: `sbx cp` to `/tmp/paddock-browser/captures/<time>-<name>`, the name reduced to safe characters), never into the operator's folders; the agent whose page it shows is told: in the Playwright tab, the session selected in that view (`BrowserCapture.selectedSessionScript`), through a note on its next command (`paddock-browser-watch --captured`); in a show tab, in the tab's history (`--operator ID screenshot|recording PATH`). For the other direction, the agent runs `playwright-cli -s=NAME show --annotate` (the wrapper requires its session and notes it): every dashboard view switches to annotation mode, the operator marks the page, types feedback, and submits, and the agent's command prints the feedback with paths to the annotated screenshot and snapshot (checked live). Meanwhile the watcher reports it (`annotate`), and the Playwright tab asks for attention (an orange dot, its icon pulsing; a closed tab comes back).
- **One command for the operator's tabs, `paddock`** (it replaced `paddock-show`; ids are `tab-` plus four hex digits; Paddock's own session for shown pages is `paddock-tabs`): `open` (a live page, or `--native` a file on the operator's screen), `annotate ID` (the operator marks up a shown page; it waits and prints their feedback and the annotated screenshot's path, run as `-s=paddock-tabs show --annotate` from `/`, so no dashboard view switches pages and the operator's view of the tab annotates its own page; checked live), `wait ID [--timeout]` (until the operator does something; exit 3 on timeout), `status`, `reload`, `back`, `goto`, `note`, `close`. Any command with an id first prints what the operator did since the agent last looked (`Paddock:` lines). Failures say why: playwright-cli's own lines without colors, and a page that did not load (a `net::ERR_*`, or still `about:blank`) suggests checking the server. A show tab's view keeps its page selected (checked twice a second) and hides the dashboard's session list only while it is; after 5 s without the page the list comes back, so "Select a session" never traps the operator.
- **Interactive tabs (OpenUI):** `paddock ui FILE` (or `-` for stdin; `paddock open x.oui` does the same) shows an OpenUI Lang 1.0 document as a purple tab, rendered on the Mac by OpenUI's own renderer: `@openuidev/browser-bundle` 0.2.1 (MIT; React 19, react-lang 1.0.1, react-ui 0.18.1 with its 84-component chat library), vendored in `App/OpenUI/vendor` by `scripts/openui-vendor.sh` (`mise run openui-vendor`; checks npm's sha512 integrity) and copied into the app as a folder. The page is Paddock's (`App/OpenUI/index.html`, `host.js`): a strict CSP (only its own files, no network, images only `data:`/`blob:`), loaded through `paddock-ui://renderer/` from a fixed list of files (`OpenUIPolicy`), WebKit content rules blocking everything else, no stored data, no windows. The agent's document is data: read from the sandbox's copy (`paddock --read ID`, at most 512 KB) and passed as a JSON string (`OpenUIPolicy.renderScript`); OpenUI runs no code from it and renders no raw HTML. The return path is the page's one message handler (`OpenUIMessage`, checked: an action must be a JSON object under 64 KB, problems are capped and text only): an action (`{type, message, context, form, values}`; Dates as ISO strings) goes to the sandbox (`paddock --operator ID action JSON`), and `paddock wait ID` prints it as one JSON line; the renderer's problems (with the component's signature as a hint) go the same way, only when they change; form state stays in Paddock's memory, so switching tabs keeps what the operator typed. A primary button validates its form first (checked live: an empty required Select sent nothing). `@OpenUrl` and links only report the URL to the agent. The agent's language reference is generated from OpenUI's own prompt generator for the same react-ui version (`Resources/openui-reference.md`, installed in the sandbox at `/usr/local/share/paddock/openui.md`), with Paddock's rules first (offline: no images or URLs; `root = Card(...)` first; one primary button per form). Checked live against the real bundle in Chromium: rendering, validation, an action with its values, problems, and restoring state.
- **Annotations that never arrived** ("Annotation client exited with code 1"): `show --annotate` runs in the session's own process, whose client finds the dashboard through a socket at `$TMPDIR/pw-<hash of $USER>/dashboard/`; the kit's startup step (no login environment) and the agent's shell saw different `USER`s, so the client never found the dashboard (reproduced, and fixed with one folder for all: `PWTEST_SOCKETS_DIR=/tmp/paddock-browser/sockets` in the kit's environment, the dashboard's start, the wrapper, `paddock`, and the watcher; `USER` no longer matters). The client's own error goes to that session's log, so `paddock annotate` names the likely cause and lists what the operator saved anyway. Annotation zips the operator saves (`feedback.md`, a screenshot, a snapshot) are unpacked beside themselves when they arrive, the `Paddock:` line quotes the comment, and `paddock feedback ID` prints every capture of a tab in full. Interactive tabs confirm each answer: "Sent to the agent" once it reached the sandbox, or why not.
- **Getting agents to use it:** sbx writes a mixin's instructions to a separate file and points to it from the agent's instructions, so the kit's `description` (what the pointer shows) says when to read it; the instructions lead with situations and the matching command and a four-step loop (show, tell them, wait, act), and `paddock` without arguments prints the same quick start.
- **What the agent sees** is written from its side, short and task-first: `playwright-cli` (open prints a session name; use it with every command; `Paddock:` lines say what the operator did) and `paddock` with the same verbs as playwright-cli (`open URL-or-FILE [--title] [--note] [--native]`, then `status`, `reload`, `back`, `goto`, `note`, `close` with the tab's id; a bare target is `open`). Messages say what to do next. Paddock's own options (`--operator`, `--read`) are not in the help.
- **Agent instructions:** how to use playwright-cli (its own work, watched in the Playwright tab) and `paddock` (anything the operator should look at, with `--native` only when sharp, selectable text matters), to show Playwright's HTML report natively by default (`paddock playwright-report/index.html --native`; it reads its data from the files beside it), not to put "(native)" in titles (the tab's color says it), the version advice below, that port 38323 is Paddock's, and to tell the operator plainly when Paddock gets in the way or lacks something (they are building it).
- The lines are untrusted (`BrowserSessions`): valid JSON under 64 KB, session names as above, `show-N` ids, at most 16 pages and 12 shows, titles and notes cleaned like terminal titles and only shown. The dashboard web view keeps no data and may reach only the dashboard's origin (`BrowserWebPolicy`); the select script is Paddock's own with a checked name, and its result is ignored.
- **Old sandboxes:** `Project.sandboxKits` records Paddock's own kits with a hash of their spec (`ResolvedKit.recorded`), so a sandbox created from an older browser kit (or gateway or OpenCode kit) shows "recreate" under Needs attention. A watcher that ends three times without a line (no `paddock-browser-watch` in the sandbox) is reported once in the status popover with that advice.
- **A project's own Playwright:** a project that pins another `@playwright/test` needs that version's browser build; the agent instructions say to run `npx playwright install chromium` in the project (the CDN hosts are allowed and `/opt/ms-playwright` is writable), not to change the project's version.
- **Open (check on the Mac, PAD-6):** that sbx 0.49.2 takes the v2 mixin with `ports` and `setup.startup` next to Paddock's v1 kits; that digest references work with `--kit`; that the published port reaches the dashboard; the memory a sandbox needs with Chromium; and whether other sandboxes with a global loopback allow can reach the dashboard's host port (deny it like a gateway port if so).
